# Добавление партиций raid.hits

**Когда:** экземпляров `hits-consumer` уже столько, сколько партиций (сейчас 12), а лаг всё равно растёт.

## Почему это не просто `--alter`

Партиция удара выбирается по хэшу ключа `raid_id`, взятому по модулю числа партиций. После увеличения числа партиций большинство рейдов переезжают в другую партицию. Удары рейда, отправленные до изменения, лежат в старой партиции, а новые — уже в другой. Консьюмеры читают партиции независимо, поэтому новые удары могут примениться раньше старых. HP останется верным, но добивающим может засчитаться не тот удар.

Поэтому перед изменением поток нужно остановить и дочитать до конца.

## Порядок

1. Объявить окно обслуживания: приём ударов на время изменения остановлен.
2. Остановить `api`, чтобы новые удары не поступали:
   ```bash
   $DC stop api
   ```
3. Дождаться, пока консьюмер дочитает всё — лаг 0 во всех партициях:
   ```bash
   kafka kafka-consumer-groups.sh --describe --group hits-consumer
   ```
4. Изменить число партиций:
   ```bash
   kafka kafka-topics.sh --alter --topic raid.hits --partitions 24
   ```
5. Обновить `hitsPartitions` в `internal/kafka/topics.go` и проверить, что кластер совпадает с кодом: `go run ./cmd/raidctl topics diff`.
6. Перезапустить консьюмеры и `api`. Клиент franz-go замечает новые партиции при обновлении метаданных, а перезапуск делает это сразу:
   ```bash
   $DC up -d --force-recreate --no-deps hits-consumer api
   ```

Уменьшить число партиций Kafka не позволяет — только создать новый топик и перенести поток.

## Проверка

`raidctl topics diff` без расхождений, лаг по всем партициям около 0, `go run ./cmd/raidctl verify` проходит.
