# Миграции схемы

Миграции лежат в `migrations/` (goose) и применяются командой:

```bash
go run ./cmd/raidctl migrate --dir migrations
```

## Правило: старая и новая версия кода работают со схемой одновременно

При раскатке какое-то время работают оба релиза, а откат кода не откатывает схему. Поэтому каждое изменение делится на два релиза (expand/contract):

1. **Expand** — добавить новое, не ломая старое: новая колонка `NULL` или с `DEFAULT`, новая таблица, новый индекс через `CREATE INDEX CONCURRENTLY`. Старый код продолжает работать.
2. Выкатить код, который пишет и читает новое.
3. **Contract** — следующим релизом убрать старое (колонку, ограничение), когда старый код уже нигде не работает.

Нельзя в одном релизе переименовывать колонку, менять её тип или добавлять `NOT NULL` без `DEFAULT`: старый код упадёт, и консьюмер уйдёт в повторы с неизвестной ошибкой (SQLSTATE 42, см. [consumer-partition-stuck.md](consumer-partition-stuck.md)).

## Порядок

1. Проверить миграцию на копии данных: время выполнения и блокировки. `ALTER TABLE` на `raid_hits` под нагрузкой держит блокировку таблицы.
2. Применить миграцию до раската кода.
3. Раскатить сервисы по одному, следя за алертами `ConsumerPartitionStuck` и `AttackErrorBudgetFastBurn`.

## Если миграция сломала обработку

Консьюмер не отправит поток в DLQ: ошибки схемы относятся к неизвестным, а если поодиночке падает каждая запись, в DLQ ничего не уходит (этап 11, A2). Повторы продолжаются до исправления. Исправить вперёд — недостающей миграцией или откатом кода ([rollback.md](rollback.md)). Ручной откат схемы — крайняя мера, только вместе с DBA.
