# Удары доходят до базы с задержкой (лаг консьюмера)

**Алерты:**
- `ConsumerLagHigh` (page): отставание группы больше 5000 записей 10 мин;
- `HitsFreshnessBudgetFastBurn` (page): больше 14,4% ударов доходят до Postgres дольше 2 с.

**Влияние.** `Attack` отвечает успешно, но HP и лидерборд обновляются с задержкой. При большом лаге босс «живёт» дольше, чем на самом деле. Удары не теряются: они лежат в Kafka.

## Диагностика

1. Посмотреть лаг по партициям. Если он равномерный, не хватает пропускной способности; если отстают одна-две партиции, они застряли.
   ```bash
   kafka kafka-consumer-groups.sh --describe --group hits-consumer
   ```
   Отстаёт одна партиция — см. [consumer-partition-stuck.md](consumer-partition-stuck.md).
2. Проверить длительность и размер пачки (панели «Длительность пачки», «Размер пачки»). Если пачки по 500 записей и долгие, упираемся в Postgres.
3. Найти блокировки и долгие запросы в Postgres:
   ```bash
   psql_q "SELECT pid, now() - xact_start AS age, wait_event_type, left(query, 80) FROM pg_stat_activity WHERE state <> 'idle' ORDER BY xact_start"
   ```
4. Посмотреть, сколько экземпляров консьюмера в группе и сколько партиций у каждого (колонка `CONSUMER-ID` в выводе п. 1).

## Действия

- **Консьюмер упал или перезапускается** — см. [service-not-reporting.md](service-not-reporting.md).
- **Не хватает пропускной способности** — добавить экземпляр `hits-consumer`. Экземпляров не может быть больше, чем партиций `raid.hits` (сейчас 12); если нужно больше — см. [kafka-add-partitions.md](kafka-add-partitions.md).
- **Медленный Postgres** — найти блокирующую сессию и снять её (`SELECT pg_terminate_backend(<pid>)`), только если она не принадлежит сервисам.

## Проверка

Лаг на панели «Лаг consumer'а» уменьшается, `raidboss:hit_stale_ratio:rate5m` ниже 0,144. После этого запустить `go run ./cmd/raidctl verify`.

## Эскалация

Если лаг растёт 30 мин после действий — разработчикам консьюмера и DBA.
