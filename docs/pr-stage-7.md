## Этап 7. Observability

### Что сделано

#### Сквозной трейс `gRPC → Kafka → consumer → Postgres → outbox → rewards-worker`

- **Продюсер** (`internal/kafka/producer.go`). У `Publish` свой span `raid.hits publish` с атрибутами `hit_id` и `raid_id`; его `traceparent` кладётся в заголовок записи Kafka. Ошибка отправки попадает в span. Контекст запроса `otelgrpc` является родителем, поэтому цепочка начинается с `Attack`.
- **Carrier** (`internal/kafka/trace.go`). `headerCarrier` реализует `propagation.TextMapCarrier` поверх `[]kgo.RecordHeader`: `Set` заменяет существующий заголовок, а не дублирует. Запись без заголовка даёт контекст без родителя, такие сообщения обрабатываются как обычно.
- **Consumer** (`hits_handler.go`, `events_handler.go`, `batchTrace`). Пачка собирается из ударов разных трейсов, поэтому одного родителя у неё быть не может:
  - span пачки (`raid.hits process batch`) — корень нового трейса со ссылками (`trace.Link`) на span'ы продюсеров. В него попадает вся работа пачки: транзакции Postgres, запись в Redis, события в outbox;
  - для каждой записи создаётся span (`raid.hits process hit`) в трейсе отправителя: его родитель — span продюсера. Он ссылается на span пачки и хранит `batch.trace_id`. По `hit_id` в Tempo видна цепочка до consumer, а подробности ведут в трейс пачки.
- **Postgres** (`internal/storage/pg`). Трейсер `otelpgx` подключён к конфигу пула: span на каждый запрос, батч и `CopyFrom`, в имени только тип операции, параметры в span'ы не попадают. `TxManager.WithinTx` открывает span `pg.tx` — родителя запросов транзакции; в нём видно ожидание соединения и блокировку `FOR UPDATE`. Вложенный вызов `WithinTx` второй span не создаёт.
- **Outbox** (`telemetry.InjectHeaders`). `traceparent` кладётся в `outbox.headers` при записи события (`RaidDefeated`, `RewardGranted`), relay переносит заголовки в Kafka как есть, и `rewards-worker` продолжает трейс пачки, в которой босс был убит.
- `telemetry.RecordError(span, err)` — единое место записи ошибки в span; `nil` игнорируется.

#### Метрики (все через OTel SDK → коллектор → VictoriaMetrics)

| Метрика | Что показывает |
|---|---|
| `rpc_server_call_duration_seconds` (`otelgrpc`) | RPS и латентность по RPC с кодом ответа (`rpc_response_status_code`) |
| `pgxpool_*` (`otelpgx.RecordStats`) | пул: занято/свободно, число и время ожидания свободного соединения (`empty_acquire*`), отменённые acquire |
| `go_*` (`contrib/instrumentation/runtime`) | горутины, память, GC |
| `raidboss_watch_subscribers`, `_rooms` | открытые стримы и рейды с подписчиками; считаются из карты рейдов при экспорте, поэтому не расходятся с реальностью |
| `raidboss_watch_slow_disconnects_total` | клиенты, отключённые за то, что не читают |
| `raidboss_kafka_consumer_lag{topic,partition}` | отставание по партициям: конец партиции из ответов брокера минус последний обработанный offset; отдельных запросов к брокеру нет |
| ранее: `raidboss_consumer_*`, `raidboss_kafka_produce_*`, `raidboss_outbox_*`, `raidboss_rewards_*` | пачки, late/duplicate/rejected удары, ошибки продюсера, размер outbox |

**Корзины гистограмм.** Границы по умолчанию в OTel SDK — `0, 5, 10, 25, …`: они рассчитаны на миллисекунды. Для величин в секундах всё, что быстрее 5 с, падает в первую корзину, и `histogram_quantile` показывает артефакт (первый замер: «p95 пачки = 4,75 с» при лаге в сотни записей). Общий `View` задаёт границы от 0,5 мс до 10 с для всех гистограмм в секундах, включая `rpc.server.call.duration` из `otelgrpc`.

**Интервал экспорта.** SDK экспортирует метрики раз в 60 с, а окно `rate(...[1m])` тогда содержит один сэмпл. В compose задан `OTEL_METRIC_EXPORT_INTERVAL=10000`.

#### Tail sampling (`deploy/otel-collector-config.yml`)

| Политика | Что сохраняет |
|---|---|
| `errors` | span'ы со статусом `Error` (серверные сбои) |
| `grpc-errors` | любой `rpc.response.status_code`, кроме `OK` и `CANCELLED` |
| `slow` | трейсы дольше 200 мс |
| `baseline` | 5% остальных |

`otelgrpc` ставит `Error` на серверном span'е только для `Unknown`, `DeadlineExceeded`, `Unimplemented`, `Internal`, `Unavailable`, `DataLoss`. `FAILED_PRECONDITION`, `RESOURCE_EXHAUSTED`, `NOT_FOUND` и подобные остаются без статуса, код лежит только в атрибуте `rpc.response.status_code` (строка). Поэтому политики `status_code` недостаточно: ошибки клиента при 5% терялись бы. `CANCELLED` исключён, чтобы каждый закрытый клиентом стрим `WatchRaid` не считался ошибкой. Условие записано через `ottl_condition`: ведёт себя явно на span'ах без этого атрибута (запросы БД, Kafka), в отличие от `string_attribute` с `invert_match`.

#### Дашборд Grafana

`deploy/provisioning/dashboards/raidboss.json` + `dashboards.yml`: 13 панелей в две колонки (пул, runtime, outbox, стримы, пачки consumer'а, late/duplicate, ошибки продюсера, лаг, RPS и p99 по RPC) с единицами измерения. Источник данных задан постоянным `uid` (`victoriametrics`, `tempo` в `datasources.yml`), иначе JSON привязан к случайному uid конкретной установки. Дашборд собран в интерфейсе и выгружен как JSON. `WatchRaid` исключён из p99: его «длительность» — время жизни стрима.

#### Логи и связка с трейсами (Loki)

- **Отправка.** `telemetry.Setup` создаёт `LoggerProvider` с OTLP-экспортёром, `telemetry.InstallLogBridge` добавляет к `slog` мост `otelslog` рядом со stdout (`slog.NewMultiHandler`). Запись уходит и в JSON-лог контейнера, и по OTLP в коллектор, оттуда конвейером `logs` в Loki (`otlphttp` на `/otlp`).
- **`trace_id` и `span_id`.** В OTLP они идут отдельными полями записи (мост берёт их из `context`), в Loki — как structured metadata. В stdout их добавляет `telemetry.WithTraceIDs`. Записи без контекста (`slog.Info`) идентификаторов не получают, поэтому логи, у которых есть активный span, переведены на `*Context`: интерцепторы (`grpc call`, паника, внутренняя ошибка, лимитер), `Attack` (ошибка публикации), `HitsProcessor` (отклонённые удары, сбои Redis), чтение лидерборда, fallback лимитера. Лог «record sent to dlq» привязан к трейсу отправителя (контекст берётся из заголовков записи): из DLQ видно, какой запрос породил запись.
- **Grafana** (`datasources.yml`): у Loki поле `derivedFields` (`trace_id` → Tempo), у Tempo `tracesToLogsV2` с запросом `{service_name="…"} | trace_id="…"`. Из лога есть ссылка на трейс, из span'а — на логи сервиса за это же время.
- Loki — один контейнер для разработки (`deploy/loki.yml`, файловое хранилище).

### Что замерено

#### Трейсы и tail sampling

`botsim`, 5 кланов × 50 игроков по 2 удара в секунду, 30 с: 2 690 ответов `OK`, 250 `FAILED_PRECONDITION` (рейды уже убиты).

| Показатель | Значение |
|---|---|
| Трейсы `Attack` с `FAILED_PRECONDITION` в Tempo | 250 из 250 (все) |
| Трейсы `Attack` с `OK` в Tempo | 130 из 2 690 ≈ 4,8% (ожидалось ≈5% плюс медленные) |
| Из них с полной цепочкой `publish` и `process hit` | 130 из 130 |

Решение принимается по всему трейсу, а не по первому span'у, поэтому хвост через Kafka не теряется.

#### Логи ↔ трейсы

После нагрузки `botsim` (250 ударов в уже убитые рейды): запись `grpc call` с кодом `FailedPrecondition` в Loki имеет `trace_id`; трейс с этим id есть в Tempo (политика `grpc-errors` его сохранила, `rpc.response.status_code = FAILED_PRECONDITION`); обратный запрос `{service_name="api"} | trace_id="<id>"` возвращает ту же запись. Оба направления проверены запросами к API Loki и Tempo; клики по ссылкам в интерфейсе Grafana не проверялись.

#### Голодание пула (`loadtest/pool_starvation.sh`)

`hits-consumer` с `PG_MAX_CONNS=16` (штатно) и `2`, одинаковая нагрузка `botsim`: 10 кланов × 50 игроков по 4 удара в секунду, `hp=10⁹` (боссы не умирают), 40 с, ≈2 000 ударов в секунду, i7-12700H, Windows, весь стек в Docker.

| Показатель | `MaxConns=16` | `MaxConns=2` |
|---|---|---|
| Ответов `OK` / латентность `Attack` p99 | 82 008 / 34,6 мс | 82 280 / 25,5 мс |
| Acquire всего | 5 325 | 4 653 |
| Acquire, которым пришлось ждать (`empty_acquire`) | 9 (0,2%) | 2 092 (45%) |
| Суммарное время ожидания свободного соединения | 0,12 с | 16 с |
| Отменённые acquire | 0 | 0 |
| Лаг consumer'а, максимум по сэмплам | 123 | 140 |
| Размер пачки p95 / длительность пачки p95 | 33 / 18 мс | 44 / 41 мс |

Голодание пула видно по `pgxpool_empty_acquire_total` и `pgxpool_empty_acquire_wait_time_nanoseconds_total` (панель «Голодание пула»): доля ожидающих acquire выросла с 0,2% до 45%, а суммарное ожидание с 0,12 до 16 секунд за 41 с прогона. Ручной прогон тех же параметров до оформления скрипта дал то же: 50% ожидающих и 22 с против 0,2% и 0,06 с.

**Что показал замер.** При этой нагрузке урезанный пул не привёл к росту лага и латентности: consumer справляется и с двумя соединениями, а голодание видно только в метриках пула. Почему именно, я не исследовал (предположительно: рейдов десять, транзакции короткие, и двух соединений хватает на очередь). Чтобы упереться в пул так, чтобы это стало видно по лагу, нужна нагрузка выше: это предмет этапов 8–9. Цифры одного прогона на каждую конфигурацию: латентность `Attack`, размер и длительность пачки между повторами заметно гуляют (p99 25–43 мс, размер пачки p95 33–72), поэтому по ним нельзя судить о влиянии пула; устойчивый результат один — рост числа и времени ожиданий.

### Принятые решения

- **Трейс пачки отдельно от трейса удара, связь через `trace.Link`.** Пачка собрана из ударов разных трейсов и не может иметь одного родителя. Цена: транзакции Postgres видны в трейсе пачки, а не в трейсе удара; переход между ними — через `batch.trace_id` на span'е записи.
- **Общий слой телеметрии только там, где он не знает про транспорт** (`RecordError`, `InjectHeaders`). Carrier и работа с `kgo.Record` остались в `internal/kafka`: брокер один, абстракция «messaging system» была бы придумана заранее.
- **`telemetry.InjectHeaders` возвращает мапу.** Запись в `nil`-мапу паникует; функция создаёт мапу при `nil`, и результат нужно использовать.
- **Метрики пула — `otelpgx.RecordStats`, а не собственные gauge.** Готовый набор уже содержит `empty_acquire` и время ожидания, нужные для диагностики.
- **Число подписчиков и лаг — observable gauge, а не счётчики вверх-вниз.** Значение считается при экспорте из реального состояния и не может разойтись с ним при повторной отписке или остановке hub.
- **`rpc.response.status_code`, а не `rpc.grpc.status_code`.** Актуальная версия `otelgrpc` пишет код строкой в новом атрибуте.
- **Постоянные `uid` источников данных Grafana.** Иначе дашборд зависит от uid, сгенерированного при первой установке.

### Известные ограничения

- **В трейсе нет span'а у `outbox-relay`.** Между записью события в outbox и началом обработки в `rewards-worker` остаётся разрыв порядка 250 мс (опрос раз в 200 мс плюс накопление пачки consumer'а); он виден как пустой промежуток в трейсе.
- **Tail sampling работает на одном экземпляре коллектора.** При нескольких решения по одному трейсу разойдутся: потребуется `loadbalancing` exporter с маршрутизацией по `trace_id`.
- **Лимит ссылок в SDK по умолчанию — 128.** Пачка до 500 записей: лишние ссылки на продюсеров отбрасываются. На span'ы записей и родительские связи это не влияет.
- **Gauge снимаются раз в интервал экспорта (10 с)** и могут пропустить короткий пик занятых соединений или лага. Для диагностики голодания надёжны счётчики `empty_acquire` и время ожидания.
- **Метрики счётчиков появляются после первого события.** `raidboss_kafka_produce_errors_total` и `raidboss_watch_slow_disconnects_total` не существуют, пока ошибок и отключений не было, панели показывают «No data».
- **Логи не сэмплируются, а трейсы — да (5%).** У записи в Loki может быть `trace_id`, трейса которого в Tempo уже нет: ссылка приведёт в пустоту. Для ошибок (серверных и клиентских gRPC) и медленных запросов трейс сохраняется всегда.
- **Не все логи имеют `trace_id`.** Логи без контекста (запуск, периодические задачи `scheduler` и `outbox-relay`, повторы пачки consumer'а, чьи span'ы создаются внутри обработчика) идентификатора не получают.
- **Tempo с локальным хранилищем временно «теряет» трейсы.** Раз в 10 минут он удаляет скомпактированные блоки, а раз в `blocklist_poll` опрашивает их список. Если опрос пересёкся с удалением, он падает (`failed to poll or create index … no such file or directory`), и поиск и `GET /api/traces/<id>` не видят часть трейсов до следующего чистого опроса, хотя на диске всё на месте (проверено: объекты после компакции сходятся, трейс снова находится). Чтобы окно было короче, `blocklist_poll` в `deploy/tempo.yml` поставлен в 1 минуту (по умолчанию 5). В продакшене с объектным хранилищем этой гонки нет.
- **Loki без аутентификации и ретеншена**, хранение на файловой системе: только для разработки.
- **Скриншоты не приложены:** цепочка одного `hit_id` в Tempo и дашборд под нагрузкой снимаются вручную в Grafana.
- В логе коллектора есть предупреждения об устаревших алиасах `otlp` и `prometheusremotewrite`; на работу не влияют.
- Тесты с `-race` не запускались локально: в окружении выключен cgo. Их прогонит CI.

### Как проверить

```bash
go test ./...                        # интеграционные тесты требуют Docker (Postgres и Redis в контейнерах)
golangci-lint run ./...
docker compose -f deploy/docker-compose.yml --profile dev up -d --build
loadtest/pool_starvation.sh          # эталон и урезанный пул; печатает таблицу метрик
```

В Grafana (`http://localhost:3000`, папка «RaidBoss Service»): дашборд RaidBoss. Трейсы — Explore → Tempo, TraceQL:

- `{ span.hit_id = "<uuid>" }` — вся цепочка одного удара;
- `{ name = "raid.hits process batch" }` — пачки consumer'а (внутри `pg.tx` и запросы);
- `{ span.rpc.response.status_code = "FAILED_PRECONDITION" }` — ошибки клиента gRPC;
- `{ name = "pg.tx" && duration > 100ms }` — медленные транзакции.

Логи — Explore → Loki, LogQL (на уровне потока только `service_name`, остальное — structured metadata):

- `{service_name="api"} | code="FailedPrecondition"` — ошибки клиента;
- `{service_name="hits-consumer"} | detected_level="ERROR"` — ошибки consumer'а;
- `{service_name=~".+"} | trace_id="<id>"` — все логи одного трейса.
