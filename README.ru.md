# raidboss

[English version](README.md)

Бэкенд клановых рейд-боссов на Go. Кланы атакуют общего босса, тысячи игроков одновременно бьют по одному запасу HP. Босс умирает ровно один раз, награды выдаются ровно один раз, лидерборд урона обновляется вживую.

![raidwatch: босс умирает под нагрузкой botsim](docs/demo.gif)

Сервис собран из gRPC, Kafka, PostgreSQL и Redis. PostgreSQL — источник правды, Kafka переносит удары и события, Redis хранит лидерборд, кэш HP и счётчики rate limit. Всё трассируется через OpenTelemetry. В README описано, что реализовано и как работает; границы текущего состояния — в разделе [Статус и ограничения](#статус-и-ограничения).

## Как это работает

### Правила игры

- У клана не больше одного активного рейда. Это обеспечивает частичный уникальный индекс в Postgres.
- Игрок бьёт только босса своего клана и только пока рейд `active`.
- Урон считает сервер: `round(power × u × crit)`, где `power` — 100–1000, `u` равномерно в [0.8, 1.2), а `crit` равен 2 с вероятностью 10%, иначе 1.
- Rate limit: 5 ударов в секунду на игрока, burst 10. Сверх лимита вызов завершается `RESOURCE_EXHAUSTED` с задержкой в `RetryInfo`.
- Удар, опустивший HP до 0, — killing blow. Удары после него не засчитываются.
- Рейд, не убитый до `ends_at`, становится `expired` и наград не даёт.
- Награды за убитого босса: `participation` (`100 + floor(1000 × доля урона)`) каждому, кто бил, `top3` (+500 / +300 / +200) и `killing_blow` (+250).
- Повтор запроса с тем же `idempotency_key` второй удар не создаёт.

### Архитектура

```
 botsim ──gRPC──► api ──produce──► Kafka: raid.hits (key = raid_id)
                   │                          │
                   │ rate limit, кэш          ▼
                   ▼                  hits-consumer ──tx──► PostgreSQL
                 Redis ◄──────────────────────┘ ZADD/SET/PUBLISH      │
                   │                                                  │ outbox
                   │ pub/sub                                          ▼
                   ▼                                            outbox-relay
   api (WatchRaid, gRPC stream) ──► клиенты                           │
                                                                      ▼
                                        Kafka: raid.events, rewards.granted
                                                      │
                                                      ▼
                                               rewards-worker ──tx──► PostgreSQL
```

| Бинарник | Что делает |
|---|---|
| `api` | gRPC API: приём ударов, стрим `WatchRaid`, лидерборд. Отдельный HTTP-порт только для pprof |
| `hits-consumer` | Читает `raid.hits`, применяет урон в Postgres, обновляет Redis |
| `rewards-worker` | Читает `raid.events`, начисляет награды |
| `outbox-relay` | Переносит события из таблицы `outbox` в Kafka |
| `scheduler` | Переводит просроченные рейды в `expired` (по умолчанию раз в 10 с) |
| `botsim` | Нагрузочный симулятор: игроки как горутины, открытая и закрытая модели нагрузки, отчёт p50/p95/p99 |
| `raidctl` | CLI: `seed`, `verify`, `rebuild-cache`, `outbox dump` |
| `raidwatch` | Терминальный клиент: живое состояние рейда через `WatchRaid` |

Топики Kafka: `raid.hits` (ключ `raid_id`, 12 партиций), `raid.events` (ключ `raid_id`, 6), `rewards.granted` (ключ `player_id`, 6) и топики для необработанных сообщений `raid.hits.dlq` и `raid.events.dlq`. Сообщения в protobuf.

### Путь одного удара

1. **`api` получает `Attack`.** Interceptor'ы идут в таком порядке: stats handler OpenTelemetry, recovery, logging, auth (игрок берётся из metadata `x-player-id`), rate limit. Rate limit — token bucket в Redis одним Lua-скриптом; время берётся через `TIME` внутри Redis.
2. **Проверки.** Игрок и рейд читаются из in-process кэша с TTL. Промах кэша идёт через `singleflight`, поэтому много одновременных запросов по одному рейду дают одно чтение из БД. Клан и статус рейда проверяются здесь для оптимизации, окончательное решение принимает консьюмер.
3. **Публикация.** `api` считает урон и отправляет `HitEvent` в Kafka с ключом `raid_id`. Клиент получает ответ после подтверждения от брокера. Успешный ответ значит «удар принят в очередь», а не «засчитан». Итог (засчитан или опоздал) приходит через `WatchRaid`.
4. **`hits-consumer`** держит по горутине на каждую назначенную партицию и копит пачки до 500 ударов или 50 мс. Пачка группируется по рейдам с сохранением порядка, дубли `hit_id` отбрасываются, а сообщения, которые не удалось разобрать, уходят в топик необработанных с причиной в заголовке. Для каждого рейда выполняется одна транзакция:
   - блокировка строки рейда (`SELECT … FOR UPDATE`);
   - если рейд не `active`, все удары считаются опоздавшими;
   - уже сохранённые удары пропускаются (поиск по `hit_id`);
   - удары применяются по порядку; первый, опустивший HP до 0 и ниже, — killing blow, остальные в пачке опоздали;
   - принятые удары записываются в `raid_hits` (с порядковым `seq`), `raid_damage` обновляется upsert'ом и возвращает абсолютные суммы;
   - обновляется `raids.hp_left`, а для убитого босса — статус `defeated`, `killer_*`, `finished_at` и в той же транзакции в таблицу `outbox` пишется событие `RaidDefeated`.
5. **После коммита** консьюмер обновляет Redis абсолютными значениями (`ZADD` для лидерборда, `SET` для HP) и публикует обновления в канал pub/sub. Offset'ы Kafka коммитятся только после обработки всех рейдов пачки.
6. **`outbox-relay`** читает неотправленные строки (`FOR UPDATE SKIP LOCKED`, пачки по 100), синхронно отправляет их в Kafka и в той же транзакции помечает отправленными. Можно запускать несколько relay параллельно. Так сохраняется порядок там, где он важен, но не глобальный порядок.
7. **`rewards-worker`** получает `RaidDefeated`, читает `raid_damage`, считает награды чистой функцией и вставляет их через `ON CONFLICT DO NOTHING`. Для реально вставленных строк пишет `RewardGranted` в outbox.

### Почему результат остаётся корректным

Kafka доставляет «минимум один раз», и код написан под это: offset'ы коммитятся только после записи в БД, а каждый шаг безопасно повторять.

- **Консьюмер упал после коммита в Postgres, но до коммита offset'а.** Пачка придёт снова. Уже сохранённые удары пропускаются по `hit_id`, повторно ничего не применяется.
- **Падение до обновления Redis.** Повтор восстановит лидерборд, потому что `ZADD` несёт абсолютные суммы. Если повтора не будет, `raidctl rebuild-cache` пересоберёт Redis из Postgres.
- **Ребаланс, при котором две копии консьюмера ненадолго обрабатывают одну партицию.** `FOR UPDATE` их сериализует, а первичный ключ `raid_hits.hit_id` не даст записать удар дважды.
- **Дубли наград.** Их отвергает уникальный ключ `(raid, player, kind)`.
- **Горячая строка.** Все удары одного рейда идут в одну партицию и одному консьюмеру, поэтому писатели не дерутся за строку босса. Это главное проектное решение, и [эксперимент ниже](#эксперимент-горячая-строка) его измеряет.

### Живые обновления: `WatchRaid`

`WatchRaid` — server-streaming RPC. Первое сообщение — `snapshot`, поэтому клиент после переподключения сразу получает текущее состояние. Дальше идут `hp_left`, `hits_total`, обновления лидерборда и финальное `finished`.

- Каждый экземпляр `api` держит одну подписку Redis pub/sub на рейд, пока у рейда есть локальные подписчики.
- Hub никогда не вызывает `stream.Send`. У каждого подписчика свой ограниченный буфер (по умолчанию 16 сообщений), а читает из него и вызывает `Send` горутина обработчика RPC. Медленный клиент не тормозит остальных.
- Когда буфер полон, одно обновление ждёт в запасном слоте. Если приходит ещё одно, пока клиент не прочитал, клиент отключается с `RESOURCE_EXHAUSTED`. Сообщение `finished` не теряется никогда.
- Обновления ограничены одним в 250 мс на рейд, накопленные значения схлопываются до последних. Все обновления несут абсолютные значения, поэтому схлопывание ничего не теряет.
- Состояние hub защищено `sync.RWMutex`. Вариант с горутиной-владельцем состояния (actor) был реализован и измерен и проиграл на нагрузке с многими рейдами и при штормах переподключений; сравнение — в [docs/pr-stage-6.md](docs/pr-stage-6.md).

### Устойчивость

- **Kafka недоступна.** У публикатора ударов ограничено время отправки и стоит предохранитель (circuit breaker). Пока он разомкнут, `api` сразу отвечает `UNAVAILABLE`, а не ждёт. Выход из этого состояния определяет проверка живости (ping брокера), а не время; после неё малая доля реальных ударов пропускается как пробы, и предохранитель замыкается после нескольких успехов и тихого периода. Клиенту безопасно повторять запрос с тем же `idempotency_key`.
- **Redis недоступен.** Rate limiter переключается с общего лимита в Redis на лимит одного экземпляра в памяти, за собственным предохранителем, чтобы упавший Redis не добавлял таймаут к каждому запросу. Лимит ослабляется до «N экземпляров × обычная норма», но не пропадает.
- **Битые сообщения.** Сообщение, которое нельзя разобрать, уходит в топик необработанных с причиной, обработка продолжается.
- **Пул PostgreSQL.** Один `pgxpool` на процесс, настраивается из env. Статистика пула публикуется как метрики, голодание пула видно на дашборде.
- **Остановка.** На `SIGTERM` gRPC-сервер делает `GracefulStop()` с таймаутом, затем сбрасывает продюсер.

### Observability

- Все сервисы отправляют трейсы, метрики и логи по OTLP в один OpenTelemetry Collector. Сервисы знают только его адрес.
- Трейсы идут через gRPC, Kafka (контекст передаётся в заголовках записей), консьюмер и Postgres, так что по одному `hit_id` в Tempo видна вся цепочка.
- Коллектор применяет tail sampling: сохраняются все трейсы с ошибками, все медленнее 200 мс и 5% остальных. Метрики уходят в VictoriaMetrics, логи в Loki.
- Среди метрик: задержка по каждому RPC с разбивкой по коду ответа, открытые стримы и отключения медленных клиентов, ошибки продюсера, размер и длительность пачки, лаг консьюмера, опоздавшие и дублированные удары, размер outbox, статистика `pgxpool` и runtime Go.
- Дашборд Grafana подключается из репозитория ([deploy/provisioning/dashboards/raidboss.json](deploy/provisioning/dashboards/raidboss.json)).

### Проверка согласованности

`raidctl verify` проверяет эти инварианты по данным в Postgres и Redis. Команда запускается после каждого нагрузочного и хаос-теста.

1. У каждого убитого рейда урон принятых ударов не меньше `hp_max`, а без killing blow меньше `hp_max`.
2. У каждого убитого рейда ровно один `killer_hit_id`, и он есть в `raid_hits`.
3. Ни один удар не применён после killing blow того же рейда (проверяется по `seq`).
4. `raid_damage` совпадает с агрегатом по `raid_hits`.
5. Не больше одной награды на `(raid, player, kind)`, и только у убитых рейдов.
6. Лидерборд в Redis совпадает с `raid_damage` после остановки нагрузки.
7. Не больше одного активного рейда на клан.

### API

`RaidService` (proto — [proto/raidboss/v1/raid.proto](proto/raidboss/v1/raid.proto)): `CreateRaid`, `GetRaid`, `Attack`, `GetLeaderboard`, `WatchRaid` (server streaming), `ListRewards`. Аутентификация упрощена: идентификатор игрока приходит в metadata `x-player-id`.

| Ситуация | Код gRPC |
|---|---|
| Нет или невалидный `idempotency_key` | `INVALID_ARGUMENT` |
| Нет `x-player-id` | `UNAUTHENTICATED` |
| Рейд или игрок не найден | `NOT_FOUND` |
| Рейд чужого клана | `PERMISSION_DENIED` |
| Рейд не активен | `FAILED_PRECONDITION` |
| У клана уже есть активный рейд | `ALREADY_EXISTS` |
| Превышен rate limit | `RESOURCE_EXHAUSTED` с `RetryInfo` |
| Очередь недоступна | `UNAVAILABLE` |
| Истёк дедлайн клиента | `DEADLINE_EXCEEDED` |

Сервер уважает дедлайны клиента: контекст запроса передаётся в Redis, Postgres и продюсер. Есть `grpc.health.v1` (`SERVING` только пока доступны Postgres, Redis и Kafka) и server reflection, который включается только при `GRPC_REFLECTION=true`.

### Модель данных

Таблицы PostgreSQL (миграции — [migrations/](migrations)): `clans`, `players`, `raids`, `raid_hits` (первичный ключ `hit_id`, порядковый `seq`), `raid_damage` (агрегат по игроку), `rewards` (уникальный `(raid_id, player_id, kind)`) и `outbox` (топик, ключ, protobuf-payload, заголовки, `sent_at`). Бинарный payload для отладки декодирует `raidctl outbox dump`.

## Эксперимент «горячая строка»

Вопрос: если каждый удар сразу обновляет строку босса в Postgres, что упирается первым — блокировка строки или пул соединений? `ATTACK_MODE` переключает `api` между тремя режимами:

- `kafka` (по умолчанию): очередь и консьюмер с пачками, как описано выше.
- `sync`: одна транзакция в запросе, `UPDATE raids … WHERE status='active'` и `INSERT raid_hits … ON CONFLICT DO NOTHING`.
- `sync-full`: тот же процессор, что в консьюмере, для пачки из одного удара прямо в запросе.

Результаты (одна машина, 30 с на ступень, дедлайн клиента 2 с, пул 16, успешных ответов в секунду):

| Целевой RPS | kafka, один босс | sync, один босс | sync, 40 боссов | sync-full, один босс | sync-full, 40 боссов |
|---|---|---|---|---|---|
| 200 | – | 190 | 189 | 191 | 189 |
| 500 | 477 | 77 | 365 | 224 | 358 |
| 1000 | 956 | 53 | 665 | 160 | 367 |
| 4000 | 3820 | 246 | 719 | 156 | 503 |

- При одном «горячем» боссе упирается **блокировка строки**, и большой пул только вредит: при 1000 RPS режим `sync` дал 424 в секунду с пулом 4 и 52 с пулом 64.
- При нагрузке на 40 боссов упирается **пул**: пул 64 даёт около 950 в секунду.
- Режим `kafka` в этом диапазоне ни одного из ограничений не показывает: p99 не выше 44 мс до 4000 RPS. Цена в том, что ответ означает «принято», а не «применено».
- Режимы `sync` не выходят на плато, а обваливаются выше примерно 200–250 RPS: запросы ждут блокировку дольше дедлайна клиента и повторяются.

Графики, методика и полная таблица 74 прогонов — в [docs/hotrow/](docs/hotrow/README.md).

## Результаты нагрузочных тестов

Открытая модель нагрузки: разгон 10 с, затем 30 с установившейся нагрузки, 40 кланов × 50 игроков, около 5% повторных запросов с тем же ключом. На одной машине работают `botsim`, все сервисы, Postgres, Kafka, Redis и мониторинг (Docker Desktop, 20 логических ядер), поэтому цифры — нижняя оценка для сервисов на разных хостах. После каждого прогона `raidctl verify` проходит.

| Целевой RPS | p50, мс | p95, мс | p99, мс | Ошибки | Макс. лаг консьюмера |
|---|---|---|---|---|---|
| 1000 | 2.2 | 5.8 | 27.1 | 0 | 138 |
| 2000 | 2.7 | 7.6 | 14.2 | 0 | 301 |
| 4000 | 4.6 | 11.8 | 20.1 | 0 | 822 |
| 6000 | 10.3 | 33.0 | 51.6 | 1 | 2391 |
| 8000 | 47.2 | 142.6 | 188.7 | 0 | 5222 |

До 4000 RPS задержки растут слабо. Между 4000 и 8000 RPS система замедляется без ошибок. Что упирается первым (`api`, консьюмер, Postgres или `botsim` на той же машине), не выяснялось.

- **1000 подписчиков `WatchRaid`** при 1000 RPS: p99 основной нагрузки 23.1 мс против 27.1 мс без подписчиков. Переподключений и отключений медленных клиентов нет.
- **Одно клиентское соединение против пула из 8** при 6000 RPS: пул оказался хуже (p99 120 мс против 75 мс). Вероятная причина — клиент и сервер на одной машине; дальше это не проверялось.
- **Хаос-сценарии** (убить консьюмер на 5 с при 1000 RPS, убить оба relay на 25 с, перезапустить Redis, остановить Kafka на 30 с при 300 RPS): после каждого `raidctl verify` проходит, потерянных и продублированных ударов и наград нет. Во время простоя Kafka клиенты получали `UNAVAILABLE`, `DEADLINE_EXCEEDED` не было.

Подробнее — в [docs/spec.ru.md](docs/spec.ru.md), раздел 11.

## Запуск

Нужны Docker, Go и оболочка bash.

```bash
loadtest/demo.sh            # сборка, инфраструктура, миграции, seed, сервисы, botsim + raidwatch
loadtest/demo.sh prepare    # только окружение
loadtest/demo.sh run        # botsim в фоне и raidwatch на экране
```

Compose-стек в `deploy/` поднимает Postgres, Kafka, Redis, OpenTelemetry Collector, VictoriaMetrics, Tempo, Loki и Grafana. Настройки берутся из переменных окружения; пример — [deploy/.env.example](deploy/.env.example). Значения там демонстрационные, для локального стенда.

Другие скрипты в `loadtest/`: `bench.sh` (лесенка RPS и тесты соединений), `hotrow.sh` и `hotrow_report.py` (эксперимент), `chaos_*.sh` (сценарии отказов).

Тесты: `go test -race ./...` (интеграционные тесты используют `testcontainers-go` и требуют Docker). CI запускает `buf lint`, `buf breaking`, проверку актуальности сгенерированного кода, `golangci-lint`, сборку и тесты.

## Статус и ограничения

- Это личный проект. В production он не развёрнут, реальных пользователей у него нет.
- Вся нагрузка синтетическая, её создаёт `botsim`. Все замеры сделаны на одной машине, по одному прогону на точку.
- Аутентификация — заглушка (идентификатор игрока в metadata). В реальной системе это был бы токен.
- Redis и Kafka в compose-стенде работают без аутентификации, с одним брокером и без репликации.
- Подробная спецификация (доменная модель, схема БД, алгоритмы, критерии готовности по этапам) лежит в [docs/spec.ru.md](docs/spec.ru.md).
